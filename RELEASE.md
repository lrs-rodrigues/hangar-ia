# Release and maintenance policy

Hangar AI follows [Semantic Versioning 2.0.0](https://semver.org/). Releases are generated by Release Please from merged Conventional Commit messages and published as GitHub Releases with an automatically maintained `CHANGELOG.md`.

## Release flow

1. A contributor opens a focused pull request against `main`.
2. Required CI, reviews, and CODEOWNERS approval pass.
3. A maintainer merges the pull request using a Conventional Commit title.
4. Release Please opens or updates a release pull request with the calculated version and changelog.
5. Maintainers review and merge that release pull request; the action creates the GitHub Release and tag.

No workflow publishes a release directly from a feature branch, pull request, or unreviewed commit.

## Commit and PR titles

Use Conventional Commits:

```text
feat: add workspace memory scope        # minor release
fix: enforce tenant filter in retrieval # patch release
docs: clarify graph provenance          # no product version change by default
feat!: replace a public API             # major release
```

Use `!` or a `BREAKING CHANGE:` footer for breaking changes. Security-sensitive changes must describe the user-facing risk and migration in the PR and release notes.

## Required GitHub protection for `main`

Configure these repository rules in **Settings → Rules → Rulesets** (or Branches):

- Target: `main`; include administrators.
- Require a pull request before merging; require at least one approving review.
- Require review from Code Owners for matching paths.
- Dismiss stale approvals when new commits are pushed.
- Require the `Repository hygiene` status check to pass; add package tests and security checks as packages are introduced.
- Require conversation resolution; block force pushes and branch deletion.
- Require signed commits when maintainers are ready to enforce it.
- Restrict direct pushes to maintainers or the GitHub Actions release bot only if the chosen release flow requires it. Prefer the release PR workflow above, which does not need a direct-push exception.

## Release roles

Maintainers control `main`, GitHub Actions permissions, protected environments, and security advisories. Contributors may propose changes but do not receive release credentials. Release automation uses the repository `GITHUB_TOKEN`; do not add a long-lived personal token unless a documented cross-repository need arises.

## Before a release

- CI and package-specific tests pass.
- Changelog and migration notes are accurate.
- Security advisories and dependency updates are evaluated.
- Published artifacts contain source revision, SBOM/provenance, and checksums once buildable artifacts exist.
